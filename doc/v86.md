# v86 in Spacewave

Spacewave uses v86 to boot small Linux guests inside the Spacewave runtime.
The current integration is centered on the Go/wazero host in
`forge/lib/v86/wazero` and the operator CLI exposed by `spacewave vm run`.
The same artifact layout also supports browser-facing demos and keeps the
emulator assets aligned with the Aperture-maintained v86 fork.

## What v86 Is

v86 is an x86 PC emulator for JavaScript and WebAssembly. The upstream project
was created by Fabian Hemmer and is maintained at
<https://github.com/copy/v86>. Upstream v86 emulates an x86-compatible CPU and
common PC devices, including BIOS boot, PCI devices, block devices, serial I/O,
NE2000 networking, and virtio-style devices. Its CPU backend translates guest
x86 machine code into WebAssembly modules at runtime, which allows a browser or
another WebAssembly host to execute Linux and other x86 operating systems.

Spacewave uses the Aperture Robotics fork at
<https://github.com/aperturerobotics/v86>. The fork tracks upstream v86 and
adds the pieces needed for the Spacewave VM path, including the TypeScript
package published as `@aptre/v86`, growable memory support, virtio-v86fs,
virtio-mem, and guest state fixes. The Rust/WebAssembly CPU backend remains
the upstream v86 backend unless a specific patch says otherwise.

## How Spacewave Uses v86

The Spacewave VM path is an embedded Linux environment for local-first demos,
integration tests, and host-side runtime experiments. The host process owns the
emulator, loads the kernel and root filesystem artifacts, exposes a filesystem
device to the guest, and optionally enables user-mode networking and JIT.

The main pieces are:

- `cmd/spacewave/cli/vm-run.go`: the `spacewave vm run` CLI.
- `forge/lib/v86/wazero`: the Go host runtime and asset loader.
- `forge/lib/v86`: shared v86 helpers and browser-facing support.
- `aperturerobotics/v86`: the v86 fork and generated emulator assets.
- `aperturerobotics/linux`, branch `v86`: the Linux kernel with v86fs support.
- `aperturerobotics/v86-debian`: the Debian root filesystem build scripts.

The runtime artifact directory must contain:

- `v86.wasm`: the v86 WebAssembly CPU backend.
- `seabios.bin` and `vgabios.bin`: BIOS files used by v86.
- `bzImage`: the Linux kernel image.
- `rootfs.tar`: the Debian root filesystem for the `v86fs` root mode.

The host can load those artifacts from an explicit artifact directory or from a
checked-out v86 tree plus a filesystem artifact directory.

## Running the VM

Build the Spacewave CLI after changing the VM command or host runtime:

```sh
cd "$HOME/company/repos/spacewave"
go build -o "$HOME/company/bin/spacewave" ./cmd/spacewave
```

Run the Debian guest with v86fs, user-mode networking, and JIT:

```sh
"$HOME/company/bin/spacewave" vm run \
  --root v86fs \
  --net \
  --jit \
  --v86-dir "$HOME/company/repos/v86" \
  --fs-dir "$HOME/.cache/spacewave/v86-artifacts"
```

The equivalent single-directory form is useful when `v86.wasm`, BIOS files,
`bzImage`, and `rootfs.tar` have all been copied into the same directory:

```sh
"$HOME/company/bin/spacewave" vm run \
  --root v86fs \
  --net \
  --jit \
  --asset-dir "$HOME/.cache/spacewave/v86-artifacts"
```

Important flags:

- `--root v86fs`: boot from the virtio-v86fs root filesystem.
- `--root-mode ram`: use the default in-memory writable guest root.
- `--net`: enable the NE2000 user-mode network stack.
- `--jit`: enable the v86 WebAssembly JIT path.
- `--v86-dir`: directory containing the v86 build output and BIOS assets.
- `--fs-dir`: directory containing Spacewave VM filesystem artifacts.
- `--asset-dir`: one directory containing every required artifact.
- `--memory-mb`: guest memory size, defaulting to 128 MiB.
- `--boot-args`: append additional Linux kernel command-line arguments.

Inside the current Debian rootfs, `eth0` is configured for the v86 usernet
defaults:

```text
address 10.0.2.15/24
gateway 10.0.2.2
dns     10.0.2.2
```

Useful guest smoke checks:

```sh
ip addr show eth0
ip route
cat /etc/resolv.conf
apt-get -o Acquire::Languages=none update
poweroff
```

Use `Ctrl-A x` to exit the emulator from the host side. A guest `poweroff`,
`halt`, `shutdown -h now`, or `reboot` should also terminate the CLI promptly
after the serial halt marker is printed.

## Building the v86 Assets

The local v86 checkout should be the Aperture fork:

```sh
cd "$HOME/company/repos/v86"
git remote -v
```

Install dependencies and build the package artifacts:

```sh
cd "$HOME/company/repos/v86"
bun install
bun run build
make all
```

Spacewave needs the generated `v86.wasm` plus the BIOS files from this checkout.
When refreshing a complete artifact directory, copy those files next to the
kernel and rootfs:

```sh
mkdir -p "$HOME/.cache/spacewave/v86-artifacts"
cp "$HOME/company/repos/v86/build/v86.wasm" \
  "$HOME/.cache/spacewave/v86-artifacts/v86.wasm"
cp "$HOME/company/repos/v86/bios/seabios.bin" \
  "$HOME/.cache/spacewave/v86-artifacts/seabios.bin"
cp "$HOME/company/repos/v86/bios/vgabios.bin" \
  "$HOME/.cache/spacewave/v86-artifacts/vgabios.bin"
```

If the exact build output path changes in the v86 fork, prefer the file that
the local v86 README identifies as the generated WebAssembly emulator backend.

## Building the Kernel

Build v86 kernels on Lima. Do not use `core@thumper` for new SkiffOS builds
while that host is reserved for other work.

The kernel source lives in the Aperture Linux fork on branch `v86`:

```sh
ssh lima 'cd ~/repos/linux && git checkout v86 && git log -1 --oneline'
```

SkiffOS is checked out on Lima at `~/repos/skiff-configs/skiff`. The active
workspace for this target is `v86min`.

Build the kernel:

```sh
ssh lima 'cd ~/repos/skiff-configs/skiff && SKIFF_WORKSPACE=v86min make br/linux-dirclean'
ssh lima 'cd ~/repos/skiff-configs/skiff && SKIFF_WORKSPACE=v86min make configure'
ssh lima 'cd ~/repos/skiff-configs/skiff && SKIFF_WORKSPACE=v86min make br/linux'
```

Do not pass an outer `-j` to these make commands. Buildroot owns its inner job
control, and the outer parallel make can corrupt or race the Buildroot target
graph.

Before copying a new kernel into the artifact directory, verify that the v86fs
patches landed in the build tree:

```sh
ssh lima 'grep -n "inode_init_owner\\|migrate_folio" \
  ~/repos/skiff-configs/skiff/workspaces/v86min/build/linux-custom/fs/v86fs/super.c'
```

Copy the built kernel to the local Spacewave artifact directory:

```sh
ssh lima 'cat ~/repos/skiff-configs/skiff/workspaces/v86min/images/bzImage' \
  > "$HOME/.cache/spacewave/v86-artifacts/bzImage"
```

The kernel config is owned by SkiffOS. If the Linux branch moves, update the
SkiffOS v86 kernel package to the exact Linux commit and rebuild through the
same Lima workspace.

## Building the Debian Rootfs

The rootfs source is public at
<https://github.com/aperturerobotics/v86-debian>. The Lima checkout lives at
`~/repos/v86-debian`.

Build the rootfs on Lima:

```sh
ssh lima
cd ~/repos/v86-debian
sudo CLEAN=1 ./build-rootfs.sh
./make-tar.sh
```

The build script creates a minimal Debian bookworm i386 filesystem with:

- BusyBox init on the serial console.
- `/proc`, `/sys`, `/tmp`, `/run`, and `/dev/pts` mounts.
- `eth0` configured for v86 usernet.
- `/etc/resolv.conf` pointing at the v86 DNS proxy.
- `poweroff`, `halt`, `reboot`, and `shutdown` commands available through
  BusyBox.
- A small operator package set for apt, networking, process inspection, and
  shell work.

Copy the rootfs tarball into the local Spacewave artifact directory:

```sh
scp lima:~/repos/v86-debian/rootfs.tar \
  "$HOME/.cache/spacewave/v86-artifacts/rootfs.tar"
```

Rebuild and recopy `rootfs.tar` whenever the guest does not contain the
expected network configuration, power-control commands, or package contents.

## Verification

The apt-over-network integration test is the highest-signal host proof for the
current rootfs, kernel, networking, and writable v86fs path:

```sh
cd "$HOME/company/repos/spacewave"
RUN_V86_APT_TEST=true \
V86_WAZERO_ASSET_DIR="$HOME/.cache/spacewave/v86-artifacts" \
go test ./forge/lib/v86/wazero \
  -run TestV86WazeroAptOverNet \
  -count=1 \
  -v \
  -timeout 20m
```

For a quick CLI smoke test, run the VM with `--net --jit` and then run:

```sh
apt-get -o Acquire::Languages=none update
poweroff
```

The expected result is that apt resolves `deb.debian.org`, downloads package
indexes through v86 usernet, and the CLI exits after guest poweroff.

## Troubleshooting

DNS failures in apt mean the guest network state does not match the expected
v86 usernet contract. Confirm the VM was started with `--net`, then check
`eth0`, the default route, and `/etc/resolv.conf`; rebuild `v86-debian` and
copy `rootfs.tar` if the rootfs does not configure them at boot.

If `--net` is not recognized, rebuild `"$HOME/company/bin/spacewave"` from the
current Spacewave checkout.

If the guest has no `eth0`, verify the kernel was built from the v86 branch and
that the VM was started with networking enabled.

If `poweroff`, `halt`, `reboot`, or `shutdown` are missing, rebuild and recopy
`rootfs.tar` from `aperturerobotics/v86-debian`.

If `poweroff` prints a halt message but the CLI does not exit, rebuild the
Spacewave CLI and rerun the guest. The host watches the serial output for the
halt marker.

If apt reaches "Reading package lists" and then takes a long time in a small
guest, that is usually dpkg's local store phase. Increase `--memory-mb` before
debugging networking.
